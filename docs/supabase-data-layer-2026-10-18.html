01

Summary

Supabase mode now refreshes sessions through Next.js 16 proxy.ts, requires a signed-in user with one club_members row, loads the nearest upcoming tournament (or the most recent past one), and persists organizer actions through RLS-scoped repositories. Writes update the UI immediately, serialize in the background, and refresh from the database after a failure. Consented photos use private storage and desk-only signed URLs. The public pairings page calls public.public_pairings(), which reads a frozen snapshot rather than the live draft. This work was rebased onto the merged Clubhouse UI; its screens still have a few demo-only data references called out below.

Questions and decisions

Sign-in method

Decision: email and password. Magic links were not built. No account creation or password-reset UI is included.

Membership profile schema

Decision: add display_name and allow roles owner, organizer, and desk so the required member contract can be populated.

Extra frontend requests

Decision: none beyond the required Desk contract. No activity table, hole-layout coordinates, or player-history feature was added.

Frozen public copy / active event

Decision: add published_snapshot and update public_pairings. Until a picker or active flag exists, the desk uses the nearest upcoming tournament, falling back to the most recent past event.

06

Schema changes

One additive migration; the initial migration was not edited. No schema was applied to a real or linked Supabase project.

Migration: supabase/migrations/20261018000000_supabase_data_layer.sql
  • club_members.display_name is added as nullable; the role check is widened to owner, organizer, and desk.
  • tournaments.published_snapshot jsonb stores the frozen public copy and has a shape check for its timestamp, signature, and groups array.
  • public.public_pairings(p_tournament) now expands only the frozen JSON snapshot, including the event name, date, start format, and first tee time. With no tournament ID it reports the nearest event’s public metadata; an unpublished event has null pairing columns. It never reads live groups or group_members.
The Supabase CLI is installed locally, but this repository has no supabase/config.toml and no linked project. Types were written by hand from the migration and should be regenerated after the owner links the project.
07

What remains demo-only or unverified

Not verified against a real project

  • No Supabase project was linked; the new migration has not been applied.
  • Club, course, tees, tournament, categories, flights, Auth user, and membership must be provisioned outside the app. The app has no service-role key or onboarding flow.
  • The current app supports one club per signed-in user; multiple memberships are rejected until a club switcher exists.
  • member.displayName is empty until provisioning fills the nullable display_name column. Roles are exposed but do not yet have different RLS permissions.

Frontend follow-ups before real use

  • The merged Setup screen still imports demo categories, tees and flights; the player profile also imports demo tee ratings instead of using the loaded Desk data.
  • The NGAP sample-file button remains visible in Supabase mode. Hide it or label it demo-only before connecting real records.
  • Activity remains session-only; hole artwork is static placeholder data; player scoring/history is still empty.
  • The login form is deliberately unstyled, and the shell has no sign-out control yet (the server action exists).
Handicap-history gap: the existing schema makes handicap_records.handicap_index NOT NULL. An imported NH row updates the current event’s frozen index to null but cannot be retained as a dated history record. A follow-up schema decision is needed if later tournaments must inherit that NH history.
Save timestamps: lastSavedAt is null after a fresh load because the current schema has no updated-at audit column; it is populated after this session’s successful writes. Multi-request actions are serialized and failures reload persisted state; draw replacement uses compensating restoration, but this is not a database transaction.

Public pairings and the clubhouse display use distinct paths: pairings read only the frozen public RPC; the spotlight remains behind the membership proxy and only signs photos with stored photo consent.

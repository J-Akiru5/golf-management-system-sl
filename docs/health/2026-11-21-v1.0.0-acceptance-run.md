# v1.0.0 acceptance test: run sheet and record

- **Status: not run.** This file is the template and the record of what the automated checks now
  cover. No organizer acceptance result is claimed here.
- **Prepared:** 21 November 2026, on `test/355-qa-coverage` from `origin/develop` `382b614`
  (v0.64.0).
- **Why it exists:** `docs/VERSIONING.md:19-21` makes a recorded acceptance test on real event data
  one of the three conditions for `1.0.0`. Finding F17 in `docs/health/2026-11-21-triage.md` records
  that no such result exists. This file supplies the sheet to run it and the place to write the
  result, so the next run can be recorded instead of remembered.
- **Not the desk script:** `docs/UAT_RUN_SHEET.md` is the existing ninety-minute desk walkthrough.
  This file does not replace it. It adds the public surfaces built since that sheet was written
  (events, concerns, Teeo, rules, the TV board, the demo request) and the evidence needed to call
  `1.0.0` accepted.

## 1. What the automated checks now cover

The browser suite is `scripts/verify-ui.mjs`, run by `pnpm check:ui`. In CI the dev server starts with
no Supabase URL, so every page serves its demo seed; a connected run takes the branches described in
section 2. Issue #355 added these sections:

| Section | What it proves |
| --- | --- |
| `public events portfolio` | `/events` lists each event on `/events/<uuid>` or says plainly that none are listed, never a sample event, and the list heading matches the count. |
| `/events/[id]` | An id the archive does not carry is a 404 with the shared not-found page; an id that is not a UUID is a 404 before any read. When the list has an event, the first one opens with its dates, venue, jump links and next actions. |
| `/feedback tick-box concerns` | The seven tick boxes (no dropdown), each follow-up appears with its tick and withdraws with it, a note with no concern is refused, a score concern without a hole is refused, and a complete note is accepted in the preview and resets the form. |
| `/demo request` | The committee copy and the one request form, the required-field refusal, and a complete request accepted in the preview. |
| `/rules and its redirect` | The address either stays on the static Conditions of Play (page, download name, open link, and the PDF answers 200 as a PDF) or forwards to an event's `#rules` section. |
| `/tv clubhouse board` | The wall shows the board, the held screen or an honest idle line; the board carries the club name, the field, the morning and afternoon split, the list label, and the pair view. |
| `Teeo concern chat` | The panel opens with the greeting and language picker, answers a quick reply from the fixed copy when no model is configured, offers the tick-box form with the page it came from, and closes with the focus back on the launcher. |

`scripts/health-check.mjs` now watches `/roster`, `/results`, `/results/all`, `/events`,
`/feedback` and `/tv` in addition to the pages it already watched. The new paths carry a title
marker, so a 200 error page cannot pass. The hardcoded IGCC host and the Bamboo Tee date window are
gone:

- `HEALTH_SITE_URL` overrides the host, so the same file can check staging.
- The event check reads `public_showcase_events` and falls back to `public_events`, the same way the
  app does. It takes the featured event, or failing that the first event open for entry, proves
  `/events` carries its name, and reports whether it is playing today. It names no club and no date.
- When nothing is featured or open, the check passes and says so. That is a quiet week, not an
  outage.

What was run for this preparation: `node --check scripts/verify-ui.mjs` and
`node --check scripts/health-check.mjs`, both clean. The parent session runs `pnpm check:ui` and the
full `pnpm check`; this file does not claim either result.

## 2. What the automated checks cannot cover

The demo build has no database. Each row below is a gap in automation, not a pass. The acceptance
run, or a connected staging run, is where these are exercised.

| Surface | Why the suite cannot prove it | Where it is covered |
| --- | --- | --- |
| A populated `/events/<id>` | No event exists in the demo archive, so only the empty list and the 404 are checked. | Step 9 of this sheet, on a connected build. |
| The `/rules` redirect | It happens only when a configured public event carries rules; the demo stays on the static page. | Step 10, on a connected build. |
| A real concern note | The suite submits only when the page says `Preview mode:`. With a database it skips the write, so it cannot fill a live inbox. | Step 11, with a named test note. |
| A real demo request | Same reason; the suite does not write to the live inbox. | Step 11. |
| Teeo with a model | With no provider configured the route answers from the fixed copy. The suite proves that fallback, not a model turn. | Step 12, on a build with a provider. |
| The TV board with real scores, and the held screen | The demo shows the sample board. Holding needs release keys held by the desk. | Step 13, with the desk holding and then releasing. |
| The live health check | The event payload check skips without `HEALTH_SUPABASE_URL` and `HEALTH_SUPABASE_ANON_KEY`; it was not run against production for this change. | Before the event, with the live values set. |
| The PDF's contents | The suite proves the file is served. It does not compare the PDF with the reading page. | Manual read once per event. |
| An older physical phone, print on the club's paper, the NGAP file, the real tee data | No automated check can. | `docs/UAT_RUN_SHEET.md` and the launch checklist. |

## 5. The run

Do the desk walkthrough in `docs/UAT_RUN_SHEET.md` first (steps 1 to 8), then the public surfaces
below. Each step records one of: **Pass**, **Pass with finding**, **Fail**, or **Not run** with the
reason.

### 9. The events portfolio

Open `/events` with no account.

*You should see:* every public event, newest first, each card with its phase, name, dates, venue and
entry count. Open one. The event page shows its dates, venue, entered count and the next actions it
can support. Try an id that is not an event: the page must be the shared not-found page, not a
guessed event.

*Record:* how many events, the one opened, and whether its pairings, results and rules sections
matched the desk's release keys.

### 10. Rules of play

Open `/rules` with no account.

*You should see:* either the event's own rules section (`/events/<id>#rules`) when the featured or
newest event carries rules, or the static Conditions of Play with the official PDF download. Open the
PDF and check it is the current document for this event. If the event has no rules text, the page
must not show another event's rules as if they were this one's.

### 11. Concerns and the demo request

Open `/feedback` with no account. Tick Score, Tee off and Others. Each follow-up should appear beside
its tick and disappear when the tick is cleared. Submit with nothing ticked: the form says to tick at
least one concern. Submit Score without a hole: it asks for the hole. Send one complete note, clearly
marked as a test, with a name and a contact address.

Then open `/demo` and send one demo request, also marked as a test.

*You should see:* the concern form's success line, and the demo request's thank-you. The organizer's
inbox should show one concern with its ticks and follow-ups, and one demo request. Nothing should
appear on a public page.

*Cleanup:* the owner or the desk removes both test notes.

### 12. Teeo

On any public page, open Teeo.

*You should see:* the greeting, the language picker (English, Tagalog, Hiligaynon, Cebuano), and the
quick replies. Send a concern in your own words. With a model configured, Teeo should ask the next
question and build the note below the conversation. With no model, Teeo must answer from the fixed
copy and offer the tick-box form. Confirm the note once; it should reach the same inbox as step 11.
Close the panel and check the launcher comes back.

### 13. The clubhouse board

Open `/tv` on the screen that will be on the wall, or at 1920 by 1080.

*You should see:* the club name, the event, the day, and the morning and afternoon lists. Switch
between By player, By pair and All days. Then have the desk hold the leaderboard: the wall must go to
the holding screen with no score on it, and come back when the desk releases it. Let it sit for two
minutes and confirm it refreshes itself.

### 14. The live health check

With the live values set:

```bash
HEALTH_SITE_URL=https://golf.syntaxure.dev \
HEALTH_SUPABASE_URL=... HEALTH_SUPABASE_ANON_KEY=... \
node scripts/health-check.mjs
```

*You should see:* every path pass, the reader pass or warn, and `public_events` name the featured or
open event and say `/events` carries it. A fail on `/tv` while the desk is holding the board is worth
checking by hand before calling it a fault.
